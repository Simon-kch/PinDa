# PinDa · 跨校园师生互助平台（可交互原型）

**连接校园，让校园生活更简单** · MORE CONNECTIONS · MORE POSSIBILITIES

面向跨校园师生用户的互助平台，两大板块：**拼拼 PINPIN**（一起出发 · 一起省钱 · 一起成长）与 **代代 DAIDAI**（你的需求 · 我来帮你）。本目录是一版完整可点击、可跑通业务流程的前端原型。

## 怎么打开

- 推荐：双击 `启动本地预览.cmd`（需要 Node.js），会自动打开 **http://pinda.localhost:5173/**
- 其它可用地址（任选其一）：
  - `http://pinda.localhost:5173/` —— 域名带 pinda，浏览器原生支持，无需改 hosts
  - `http://127.0.0.1:5173/pinda/` —— 路径带 pinda，任何浏览器都能用
  - `http://127.0.0.1:5173/index.html` —— 原始地址
- **手机 / 其它电脑**：连同一个 Wi-Fi，访问启动时窗口里打印的那个地址，形如 `http://192.168.x.x:5173/`（本机当前是 `http://10.13.87.142:5173/`）。服务同时监听局域网，所以同一网络下的设备都能打开。
- 最简单（不启动服务）：双击 `index.html`。这种方式能完整演示，但验证码只能走演示模式（页面显示验证码），数据也仅保存在本机浏览器。

> **为什么 `pinda.localhost` 在别的设备上打不开**：`localhost` 是保留域名，按标准永远解析成本机回环地址（127.0.0.1 / ::1）。换句话说，每台设备打开 `pinda.localhost` 都是在找**它自己**上的服务——你手机上没有跑这个服务，自然打不开。这不是配置错误，是这个域名的定义。
>
> 所以：**本机用 `http://pinda.localhost:5173/`，其它设备用 `http://<本机局域网IP>:5173/`**（启动窗口会打印）。想要一个任何设备、任何网络都能打开、且网址带 pinda 的公网地址，需要部署，见文末「上线」。

**其它设备连不上时按顺序排查**

1. 两台设备是否在**同一个 Wi-Fi**（手机热点也行，把电脑连到手机热点，手机就能访问电脑的局域网地址）
2. Windows 防火墙是否放行：控制面板 → Windows Defender 防火墙 → 允许应用通过防火墙 → 勾选 Node.js 的「专用」和「公用」；或以管理员身份执行
   `netsh advfirewall firewall add rule name="PinDa 5173" dir=in action=allow protocol=TCP localport=5173`
3. 校园 / 公共 Wi-Fi 常开启「客户端隔离」，同一网络下设备之间也互相不通；这种情况下换手机热点，或改用内网穿透（下方「上线」）
4. 每台设备的数据是独立的：账号、订单存在各自的浏览器 localStorage 里，你电脑上注册的账号不会出现在手机上

**安全提醒**：开放局域网后，同一 Wi-Fi 下的人都能访问这个站点。验证码接口自带限流（每 IP 每小时 30 次、每邮箱每天 10 次、60 秒重发冷却），但仍不建议在不可信网络里长期开着。不需要局域网访问时，在 `config.json` 里加 `"lan": false` 后重启，服务就只监听本机。

- 数据保存在浏览器 localStorage，可随时在「个人中心 → 重置演示数据」恢复初始状态。

### ② 临时公网隧道（推荐给评委/同学演示）

双击 `共享给他人.cmd`（前提：先双击 `启动本地预览.cmd` 把本站跑起来），脚本会通过 localhost.run 建立一条公网隧道，打印出一个 `https://xxx.lhr.life` 链接——任何设备、不用连同一个 Wi-Fi 都能打开，手机扫终端里的二维码也行。

- 链接是**随机名字**，不含 pinda；想要带 pinda 的公网网址只能用方式 ③，或在 localhost.run 注册账号绑定自己的域名
- 链接**随窗口关闭立即失效**，服务窗口也必须一直开着
- 链接**是公开的**：知道链接的人都能访问。验证码接口已加保护（只允许校园邮箱、每 IP 每小时上限、每邮箱每天上限、全站每日上限），演示完记得关窗口

### ③ 正式部署（长期可用）

本项目的静态部分可以直接丢到 Vercel / Netlify / Cloudflare Pages；发信接口需要一个能跑 Node 常驻进程的平台（Render、Railway、Fly.io 或自己的服务器），把 `server.js` 挂上去即可，因为它就是一个标准的 Node HTTP 服务：

1. 平台新建 Web Service，启动命令 `node server.js`，环境变量填 `VEGA_SMTP_HOST / VEGA_SMTP_PORT / VEGA_SMTP_SECURE / VEGA_SMTP_USER / VEGA_SMTP_PASS / VEGA_MAIL_FROM`（这样就不需要 config.json，凭据只存在平台的环境变量里）
2. 绑定域名（如 `pinda.你的域名.com`），配好 HTTPS
3. 在 `config.json` / 环境变量里把 `allowedOrigins` 设成你的域名，并把 `lan` 设为 `false`

注意：验证码目前存在服务端内存里，所以部署时要选**单实例常驻**的服务（Render/Railway/VPS 都可以）。如果用 Vercel 这类函数计算，需要改成 Redis 之类的共享存储，否则校验可能落在不同实例上而失败。

注册/认证时的验证码由**本地服务器**生成并通过 SMTP 发送到同学的校园邮箱，校验也在服务端完成。前端拿不到邮箱账号与授权码，也不参与判定。

**开启真实发信只要两步**

1. 双击 `配置邮箱.cmd` —— 引导式向导会问你三个问题（用哪个邮箱、发件邮箱地址、授权码），自动写好 `config.json`，并**当场发一封测试邮件**给你确认。授权码在输入时是打码的，只保存在你本机，不会出现在聊天记录或任何网络请求里。
2. 收到测试邮件后，双击 `启动本地预览.cmd` 即可。

向导会自动识别常见邮箱：QQ 邮箱、网易 163、腾讯企业邮、Outlook / Microsoft 365、Gmail，也可以手填自建 SMTP。发信失败时它会用中文指出出错环节（端口、加密方式、授权码、收件人被拒…）并给出具体改法，改完再运行一次向导即可。

也可以手动配置：把 `config.example.json` 复制为 `config.json` 后自行填写。

```json
{
  "smtp": {
    "host": "smtp.qq.com",
    "port": 465,
    "secure": true,
    "user": "你的邮箱@qq.com",
    "pass": "邮箱授权码",
    "from": "你的邮箱@qq.com",
    "fromName": "PinDa 校园互助平台"
  }
}
```

控制台会明确打印当前模式：

- `邮箱验证码：真实发送（SMTP smtp.qq.com:465，发件人 …）`
- `邮箱验证码：演示模式（未配置 SMTP，验证码直接显示在页面上）`

**没配置 SMTP 时**：自动进入演示模式，验证码直接显示在页面上，便于演示与开发，功能不受影响。

**已内置的保护措施**

| 项目 | 说明 |
| --- | --- |
| 域名白名单 | 只接受高校校园邮箱（`*.edu.cn` / `*.edu`），其它邮箱直接拒绝；示例数据用的是西浦域名 |
| 重发冷却 | 同一邮箱 60 秒内只能发送一次（可在 config.json 调整 `resendSeconds`） |
| 每日上限 | 同一邮箱每日最多 10 次，防止被当成骚扰工具 |
| IP 限流 | 同一 IP 每小时最多 30 次请求 |
| 尝试次数 | 单个验证码最多试 5 次，超出即作废 |
| 一次性 | 验证码校验通过后立即失效，不可重放 |
| 失败可重试 | 发信失败会回滚计数，修好配置后能立刻重发，不会被冷却锁住 |
| 全站每日上限 | 默认每天最多 300 封（`dailyTotal`），即使链接被陌生人拿到也不会刷爆邮箱 |
| 来源白名单 | 可选，配置 `allowedOrigins` 后只接受来自你自己域名的请求（部署到固定域名时建议开启） |
| 凭据隔离 | SMTP 账号与授权码只存在于服务端 `config.json` / 环境变量，且 `config.json` 禁止被下载（403） |
| 传输安全 | 默认强制 TLS；明文调试模式仅在 SMTP 指向本机回环地址时生效，防止真实邮箱被明文发送 |

**关于账号体系**：验证码这一环节已经是真实的（服务端生成 + 服务端校验 + 真实邮件），但账号、订单等业务数据目前仍保存在浏览器本地，属于原型设计。要彻底防作弊，下一步是把用户与订单也搬到后端，可以在此基础上继续。

## 首页首屏星空（真实星图）

**只有首页顶部那块黑色首屏**换成了一片会动的真实星空，页面其余部分、以及登录/注册/应用内页都保持原来的米白配色（避免影响阅读）。它不是随机星点，而是按真实星表做的球面投影：

| 项目 | 说明 |
| --- | --- |
| 数据来源 | [d3-celestial](https://github.com/ofrohn/d3-celestial) 公开星表（星等 ≤5.5，2950 颗恒星）与星座连线（12 个星座、28 段） |
| 文件 | `assets/data/sky.json`（约 82KB）+ `assets/js/skymap.js`（渲染引擎） |
| 投影 | 立体投影，视场中心对准北天极附近，赤经赤纬 → 屏幕坐标（首屏尺寸自适应） |
| 动效 | 天球绕北极星自转（约 19 分钟一圈）、星点轻微闪烁、鼠标视差；开启系统「减少动态效果」自动变静态 |
| 指引寓意 | 金色虚线画出**北斗七星 → 北极星**的指北延长线；**织女星（PinDa）**与北极星之间也有连线并单独标注 |
| 性能 | Canvas 绘制，视场内约 1100+ 颗星；按 DPR 渲染，页面不可见时自动暂停 |

为什么是星空：PinDa 的星空意象对应「连接校园里的人和需求」；星图本来就是最古老的导航工具——古人靠北斗指北，郑和下西洋用「牵星术」定位。首页把「找路」与「在校园里找到合适的人」对应了起来。

需要更新星表时运行：

```
node work/build-sky.js      # 重新抓取星表并生成 assets/data/sky.json 与 assets/js/sky-meta.js
```

星图只挂在首页首屏（`assets/js/views.public.js` 的 `landing()` 里那个 `<canvas id="sky-hero">`，由 `app.js` 的 `syncSky()` 挂载）。想在别的页面也铺星空，在那个页面的容器里加一个同样 class 的 canvas 并在 `syncSky()` 里一起挂载即可。

## 从策划材料提炼并落地到网站的内容

**目标用户与痛点（来自组员访谈）**

- 太仓校区学生的日常出行难题：园区—太仓双校区班车不够充足，顺风车价格高且不放心
- 代购、代取、代办需求分散，网上代购费贵且骗子多，缺少安全可靠的平台
- 小组作业找不到合适搭子，学生的时间与资源没有被充分利用

**四大场景（海报原文）**

- 拼拼：拼车出行（上下课／机场／周边游）、拼单购物（团购／省钱／更划算）、找搭子（学习／运动／生活）、合作机会（项目／资源／互助）
- 代代：出国代购（海外好物轻松带回）、超市代取（生活用品快速送达）、校园代办（排队／取件／跑腿）、更多需求（定制服务随时响应）

**问题 → 方案 → 优势**

- 我们发现的问题：需求难以找到合适的人；需求分散缺乏可靠平台；学生时间与资源未被充分利用
- 我们的解决方案：一站式互助平台；精准匹配需求与资源；保障交易安全与信任；让学生的时间与能力创造更多价值
- 我们的核心优势：精准定位跨校园师生群体；多元化服务场景；安全可靠的交易机制（真实身份认证 + 评价体系）；双向价值创造（用户需求 + 学生资源 = 共赢）

落地位置：落地页对应板块、「拼拼 / 代代」介绍页、平台规则页，以及应用内的分类与流程设计。

## 商业化：六个收入点 + 三阶段推进

策划组结论是「不要把六种收入一开始全做起来」，网站把它做成了**可切换的运营阶段**（管理台 → 商业化）。

| # | 收入来源 | 启用阶段 | 原型状态 |
| --- | --- | --- | --- |
| 1 | 拼拼订单服务费（拼车小额服务费、拼单透明服务费；搭子基础免费） | 2 / 3 | 已实现（服务费引擎） |
| 2 | 代代代办订单抽成（按约定比例） | 2 / 3 | 已实现（佣金引擎） |
| 3 | 校园商家推广费（月度套餐 + 可追踪优惠券） | 2 / 3 | 已实现（优惠券模块 + 后台统计） |
| 4 | 付费增值服务（信息加曝光、合作项目发布、组织管理工具） | 2 / 3 | 已实现（加曝光购买） |
| 5 | 商家与校园组织合作（社团团购、活动报名、出行拼车） | 3 | 规划中 |
| 6 | 会员 / 订阅服务（高频用户权益、商家套餐、社团订阅） | 3 | 已实现（会员中心） |

**三个阶段**（管理台一键切换，收费规则实时生效）

1. 项目启动：拼拼、代代全部免费，重点验证订单量、完成率、用户复购率，先建立用户基础
2. 收入验证：代代订单抽佣 6% / 会员 2%，拼单收 ¥1/单 小额服务费（会员免收）；拼车与搭子仍免费
3. 规模扩张：拼车、拼单、合作机会开始收小额服务费，叠加商家推广套餐 ¥199/月、信息加曝光 ¥1.9/次、会员订阅等稳定收入

**答辩要点**（已收录在管理台「商业化」面板）

1. 为什么学生不直接在微信群里拼车、找搭子？→ 需要比微信群更明确的分类、需求匹配、信用评价和交易流程
2. 为什么用户愿意付服务费？→ 节省时间、提高匹配效率、降低沟通成本、获得更可靠的服务；基础功能免费，只在产生明确价值处收费
3. 怎样避免有订单却不赚钱？→ 计算支付成本、退款、纠纷处理、客服与推广支出；低金额订单设最低服务费；明确服务边界、责任分配与适用规则

## 功能清单

**账号与身份认证**

- 手机号注册（昵称、校区、专业、年级、一句话介绍），注册即送 ¥100 体验金
- 校区只有两个选项：`SIP`（苏州工业园区校区）与 `TC`（太仓校区）
- 专业为下拉选择，示例库取自西浦官网「教学」栏目：本科 52 个 + 硕士 72 个 + 博士 17 个，共 141 个，按层次分组；含「还未选择专业」与「其它专业（不在列表中）」，其它学校的同学可直接手填
- 身份认证：学号 + 校园邮箱验证码（一次性、10 分钟有效）；未认证也可先注册，之后在个人中心补认证
- 两种登录方式：手机号登录 / 学号登录（均为 PinDa 平台密码，不涉及学校密码）

**拼拼 PINPIN**

- 四类信息：拼车出行、拼单购物、找搭子、合作机会（小组作业组队、创业比赛、社团招募）
- 拼车支持常用线路一键填入（太仓校区 ↔ 南校区、苏州 ↔ 虹桥/浦东、苏州站、硕放机场）
- 拼车详情带出行安全提示（认证状态、信用分、车型座位、行程一键分享给同学或家人）
- 按类型、校区、关键词筛选；会员可用「只看会员发布」与信用分高级筛选
- 加入 / 退出拼拼、成员进度、联系方式打码（消耗每日额度查看，会员不限次）
- 发起人「成团并结算」→ 自动为每位成员生成账单 → 支付 → 交付确认 → 按当前阶段规则结算

**代代 DAIDAI**

- 双身份：发布「代购需求」或挂出「可以帮带」的行程
- 五类：出国代购 / 超市代取 / 校园代办 / 跑腿带饭 / 灵活定制
- 接单或下单即生成订单，状态流转留痕（待支付 → 进行中 → 已交付 → 已完成 / 已取消）
- 代购费支持两种计法：≤50 视为百分比，>50 视为固定金额

**校园优惠（商家推广）**

- 合作商家展示（付费推广位 + 「推广中」标识）、优惠券领取、一次性券码、到店核销
- 后台可新增商家与优惠券、暂停/恢复推广，并统计领取量、核销量、核销率与月度推广收入

**交易、费用与钱包**

- 免费场景在订单里明确标注「本阶段免收」，不做模糊收费
- 钱包：余额、累计收入 / 支出 / 平台费用、充值提现（模拟）、全部流水
- 增值服务：信息加曝光 ¥1.9（24 小时置顶，带「⚡ 已加曝光」标识，优先于普通会员展示；会员自身已享优先展示，无需重复购买）
- 评价体系：评分影响对方好评率与信用分

**管理台（管理员）**

- 数据概览：用户与会员占比、累计佣金、商家推广收入、会员费收入、GMV、近 7 日佣金趋势、代代分类分布
- 商业化：三阶段切换、六个收入来源对照（启用阶段 / 是否已实现）、关键指标（订单量、完成率、复购率）、收入结构、答辩要点
- 商家与推广：商家入驻与月度套餐、优惠券上下架、核销追踪
- 用户与会员：手动开通/续费/取消会员、调整信用分

## 登录与身份认证（重要）

**PinDa 不使用、也不会索取任何学校的统一身份账号密码（例如西浦 e-Bridge）。** 原因不是技术上做不到，而是不该做：

- 多数高校的统一身份系统没有对外开放第三方登录（OAuth / OIDC）接口，"帮你去登录"只能由平台经手同学的密码，属于凭据代持——这正是钓鱼网站的标准特征。
- 密码一旦离开学校页面，就可能被记录、泄露或滥用；未授权访问学校系统还可能触及《网络安全法》《刑法》285 条与学校 IT 使用规范。
- 页面上有「为什么不用学校账号直接登录？」的说明入口，登录页与注册页都有明显提示。

**身份核验方式**：学号（6–12 位数字）+ 校园邮箱验证码（`*.edu.cn` / `*.edu`）。平台只保存学号与校园邮箱，认证后获得「已认证」标识。

**验证码投递方式**：启动本地服务器并配置 SMTP 后，验证码会真实发送到同学的校园邮箱（见上文「邮箱验证码」）；未配置时退回演示模式，验证码直接显示在页面上，方便演示。

**若要实现真正的一键登录**：向你所在学校的 IT / 学生事务申请官方 SSO 授权。拿到授权后，登录跳转到学校官方页面，学校只回传学号与邮箱，平台全程接触不到密码。代码里已预留对接位置：替换 `assets/js/data.js` 中的 `V.sendCode / V.checkCode / V.verifyStudent` 为 OIDC 回调即可。

## 后续对接设计稿

1. 全局换肤：`assets/styles.css` 顶部的 `:root` 变量（金/墨/米白、圆角、阴影、字号）改一遍即可整体换风格。
2. 品牌视觉集中在 `styles.css` 末尾的「PinDa 品牌视觉」段落（Logo 尺寸、海报卡片、三栏卡、愿景块、阶段卡、优惠券）。
3. 页面级调整：每个页面一个渲染函数（落地页 `views.public.js → landing`，拼拼 `views.market.js → pinpin`，优惠 `views.deals.js`，管理台 `views.admin.js`）。
4. 收费规则改一处即可：`data.js` 的 `DEFAULT_SETTINGS` 与 `V.STAGES`，后台「商业化 / 平台设置」也能实时改。

## 已知边界（原型阶段）

- 支付、短信/邮件验证码、学生认证、提现、券核销均为模拟，不产生真实资金与信息发送。
- 商家与校园组织合作（收入点 5）尚未实现，管理台中标注为「规划中」。
- 费用结算时点为「交易完成时」，按完成时的运营阶段与身份计费；已完成订单不受阶段切换影响。
- 拼车、跨境代购与代办涉及不同的安全、合规与责任问题，原型已在规则页声明服务边界；正式运营前需以《服务协议》明确责任分配。
- 未接入任何学校的统一身份系统（如西浦 e-Bridge），也不会接入其账号密码（见上文「登录与身份认证」）。

## 上线（想要别人也能访问的 pinda 网址）

本地地址只在你这台电脑可用。要让同学访问，需要两步：

1. 把站点部署到一台有公网的服务上（云服务器 / Vercel / Netlify 等）。本项目是纯静态站点 + 一个 Node 发信服务，静态部分直接上传即可；发信服务用 `server.js`（把 `PORT` 与 `SMTP` 配置换成线上值，并用 pm2 或 systemd 常驻）。
2. 绑定一个带 pinda 的域名，例如 `pinda.xjtlubbs.com`、`pinda-campus.cn`，或平台免费给的二级域名 `pinda-pinpin.vercel.app`。域名解析到服务器后，把 `PORT` 暴露为 80/443 并配好 HTTPS（证书可用 Let's Encrypt 免费申请）。

注意：线上环境务必保留「验证码只能在服务端校验」「config.json 不对外可读」「只允许校园邮箱」这三条设置，最好再给 API 加上真正的域名校验与更严的限流。
